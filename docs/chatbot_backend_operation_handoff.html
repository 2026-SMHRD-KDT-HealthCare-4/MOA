MOA 챗봇 백엔드 운영 전환 상의·인수 문서

대상: 백엔드 담당자 · 목적: 룰 기반 대화 제어의 운영 전환 전 안전 정책 및 세션 상태 저장 합의

현재 개발용 /chat/dev에는 룰 기반 1차 검사 → LLM → 룰 기반 최종 보정 흐름이 적용되어 있습니다. 운영 전환 시에는 아래 두 항목을 팀 정책으로 확정한 뒤 운영용 /chat와 DB에 반영해야 합니다.

1. 결정이 필요한 항목

우선 합의 대상 A — urgent_alert 정책
긴급 기준, 즉시 동작, 오탐 처리, 사용자 면책 문구는 안전과 직접 연결되므로 프론트 또는 LLM이 임의로 결정하지 않습니다.
우선 합의 대상 B — ChatSession 상태 필드
현재 주제와 질문 순번을 세션에 저장해야 앱 재진입·새로고침 뒤에도 대화 맥락을 안정적으로 이어갈 수 있습니다.

2. urgent_alert 운영 정책

2-1. 권장 분류 기준

등급룰 예시백엔드 최종 응답권장 동작
긴급자살·자해“죽고 싶어”, “살기 싫어”, “사라지고 싶어”, “그만 살고 싶어”user_intent=negative_mood
bot_emotion=worried
next_action=urgent_alert		고정 안전 문구 반환, 보호자 알림 후보 생성, 즉시 연락 수단 안내
긴급신체 응급“쓰러질 것 같아”, “가슴이 답답해”, “숨이 안 쉬어져”, “심하게 어지러워”user_intent=health_discomfort
next_action=urgent_alert		고정 안전 문구 반환, 119·주변 도움 요청 안내, 보호자 알림 후보 생성
주의일반 불편“아파”, “불편하다”, “어지럽다”, “힘들다”next_action=continue공감·휴식·가족 알림 권유. 자동 긴급 알림은 보내지 않음

2-2. 즉시 동작: 팀 합의 필요

  • 앱 응답: LLM 문구를 쓰지 않고 백엔드의 고정 안전 문구를 반환한다.
  • 보호자 알림: 활성 보호자 연결 및 알림 동의가 있을 때만 생성할지 결정한다.
  • 반복 억제: 동일 세션·동일 등급 알림은 예: 15분 쿨다운으로 중복 발송을 막는다.
  • 기록 범위: 원본 음성은 저장하지 않고, 발생 시각·등급·규칙 ID만 최소 저장하는지 결정한다.

2-3. 오탐 처리 권장안

명확한 긴급 키워드가 있으면 확인 질문 때문에 안내·알림을 지연하지 않습니다. 다만 “죽겠다”처럼 문맥이 불명확한 표현은 안전 확인 문구를 즉시 보여준 뒤 사용자가 오탐임을 명시적으로 취소할 수 있게 합니다. 취소하더라도 해당 턴의 안전 규칙 적용 사실은 최소 감사 로그로 남기는 방안을 권장합니다.
  • 사용자 취소 UI/음성: “괜찮아요”, “실수예요”, “알림 보내지 마세요”
  • 백엔드 상태: alert_status=pending | cancelled | sent
  • 취소 후에도 대화는 negative_mood 또는 health_discomfort 맥락으로 안전하게 이어간다.

2-4. 고정 면책·안내 문구 권장안

상황권장 문구
자살·자해 위험“지금 많이 힘드신 것 같아요. 혼자 계시지 말고 가까운 가족이나 119에 바로 도움을 요청해 주세요. 모아는 의료 진단이나 긴급 구조를 대신할 수 없어요.”
신체 응급 위험“지금은 바로 주변에 도움을 요청해 주세요. 증상이 심하거나 숨쉬기 어렵다면 119에 연락하는 것이 좋아요. 모아의 안내는 의료 진단을 대신하지 않아요.”
일반 불편“몸이 불편하셨군요. 무리하지 말고 쉬어 주세요. 불편함이 계속되거나 심해지면 의료진 또는 가족에게 알려주세요.”

3. ChatSession 필드 추가 제안

개발용 API는 프론트가 매 턴 conversation_topic, question_index를 전달합니다. 운영에서는 아래 최소 필드를 세션에 저장하는 방식을 권장합니다.

필드타입·기본값용도
conversation_topicVARCHAR(20), NULLmeal | sleep | health | mood | family 중 현재 질문 주제. NULL이면 새 대화
question_indexINTEGER, NOT NULL, DEFAULT 0각 주제의 메인/후속 질문 순번. 주제 전환 시 0 또는 1로 초기화
last_rule_actionVARCHAR(20), NULLcontinue | finish | navigate | urgent_alert의 마지막 결정값. 운영 디버깅·안전 감사용
last_active_atTIMESTAMP, NULL세션 만료·재개 판단. 예: 30분 이상 비활성이면 주제 초기화

3-1. 운영 처리 규칙

  • 현재 주제와 동일한 발화면 question_index를 증가시켜 후속 질문을 선택한다.
  • 다른 intent/topic이면 새 주제로 바꾸고 question_index를 초기화한다.
  • finish면 ended_at을 기록하고 세션을 종료한다.
  • navigate는 주제 상태를 유지할지, 기능 이동 후 새 세션으로 둘지 팀에서 결정한다.
  • 음성 원문·원본 음성 저장은 기존 ZDR 정책과 분리해서 검토한다.

4. 운영용 API 전환 체크리스트

  • /chat도 /chat/dev와 동일한 최종 JSON 규약을 사용한다.
  • 응답 필수값: reply, user_intent, bot_emotion, next_action, route, conversation_topic, question_index
  • LLM 입력 전·후에 동일한 룰 검증을 적용하고, 위험·종료·기능 이동은 룰 값을 우선한다.
  • OPENAI_API_KEY, OPENAI_CHAT_MODEL, 알림 발송 환경변수를 운영 환경에 설정한다.
  • 테스트: 긴급 키워드, 오탐 취소, 기능 이동, 주제 전환, 세션 재개, 알림 쿨다운을 각각 검증한다.
